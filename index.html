Selected investigations

Performance, security, reliability, static analysis and third-party audits. Status as of October 19, 2026. Performance measurements were taken on IntelliJ IDEA 2026.2.3, with each test attached to its ticket; security findings were checked against OSV for the exact pinned version. The fixes sent to JetBrains are open pull requests awaiting review.

No. 01 · Performance

IJPL-257909

IntelliJ Platform · Settings › Plugins · UI thread

Pull request #3701 · open, awaiting review

Opening Settings › Plugins took most of a second

Cause
For each installed plugin, the page rebuilt the plugin and module maps and walked the dependencies of every essential plugin, on the UI thread. The cost grows with the square of the number of installed plugins, and the source code already had a FIXME about it.
Intervention
Compute the set of plugins that essential plugins require once per plugin set, then look each plugin up in it. The cache is dropped when the plugin set is replaced.
Result
With 158 plugins loaded, the page took 689–931 ms to open. One walk plus a lookup per plugin takes 8–22 ms and gives the same answer for all 158.

Ticket and measurement testPull request #3701

No. 02 · Security

reactive-commons-go#5

Bancolombia · Go messaging library · dependencies

Fixed by the maintainers · October 7, 2026

A messaging library pinned to a dependency with three critical advisories

Cause
The library’s go.mod pinned github.com/rabbitmq/amqp091-go at v1.10.0, inside the affected range of 10 advisories published in September 2026: 3 critical (a missing TLS minimum version in the URI parser, frame injection through an integer overflow, and silent truncation of short strings) and 7 high.
Intervention
A report to the maintainers with every advisory checked against OSV for the exact pinned version, and the version that fixes all of them (v1.13.0).
Result
From 10 advisories to 0 in OSV: the maintainers upgraded to v1.15.0 in pull request #6 and closed the report 3 days after it was filed.

No. 03 · Third-party audit

lsp4ij#1540

Red Hat · LSP4IJ plugin · UI thread

Fixed by the maintainer · October 9, 2026

A language-server client detecting file types on the UI thread

Cause
LSPBreadcrumbsRefreshListener.breadcrumbsChanged() runs on the UI thread and requested document symbols there, which reaches file-type detection that can read the file content. The issue had been open since May 2026.
Intervention
A report to the maintainer with the exact path in the current code and a suggested fix: run the request on a pooled thread and keep only the restart on the UI thread.
Outcome
The maintainer made that change the same day and closed the issue. Impact, stated plainly: one slow call per open file each time a language server starts.

No. 04 · Reliability

IJPL-200871

IntelliJ Platform · workspace model · concurrency

Fixed by JetBrains · September 9, 2026

A ConcurrentModificationException in the workspace model

Cause
WorkspaceFileIndexDataImpl.fillPackageFilesAndDirectories() iterates an unsynchronized LinkedHashMap that can change in the middle of the iteration.
Intervention
Root-cause analysis posted on the ticket. It located that iteration and proposed a ProgressManager.checkCanceled() call.
Outcome
JetBrains fixed the ticket with a different change: the package-name queries now bring the index up to date before reading it.

Ticket and analysisCommit e1d600df

No. 05 · Static analysis

IDEA-393501

IntelliJ IDEA · Java › Tests · read actions

Filed · assigned to a JetBrains developer, open

A freeze pattern inside IntelliJ’s own test search

Cause
SearchForTestsTask runs in the background but calls onFound() through the blocking ReadAction.run(), with no checkCanceled() anywhere in the class. JetBrains’ Platform Blog names this pattern as a recurring cause of UI freezes.
Intervention
Found by Background ReadAction Freeze Companion, a static check for this pattern. A follow-up showed why a plain switch to a non-blocking read action is not safe here: onFound() writes files, and a restarted read action would write them again.
Outcome
JetBrains moved the ticket to the IDEA project and assigned it to a developer. Both calls are still on master as of October 2026.

Engineering

How an investigation runs

The same method applies to a slow IDE, a vulnerable dependency and a crash in a platform tracker.

  1. 01

    Find the gap

    Start from evidence someone can point to: a freeze report, a published advisory, a crash in a tracker, a check that no tool makes. Reproduce it on the exact version where it happens.

  2. 02

    Understand the cause

    Follow it to the code that causes it: the method that spends the time, the dependency version inside an advisory’s affected range, the iteration that is not synchronized. Keep the reproduction as a test or a check that anyone can run again.

  3. 03

    Build the fix

    Ship the smallest change that removes the cause, with evidence before and after: a pull request upstream, a report to the maintainers, or a plugin when the fix belongs outside the platform.
