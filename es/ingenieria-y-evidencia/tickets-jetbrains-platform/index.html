Tickets de JetBrains Platform

Errores en el propio código de JetBrains, documentados públicamente en su tracker YouTrack: dos presentados directamente después de que un control de este catálogo los encontrara en el código de IntelliJ, más análisis de causa raíz publicado en tickets existentes de IntelliJ Platform (IJPL), y un arreglo enviado como pull request.

Presentado directamente

Errores encontrados en el propio código de IntelliJ por un control de este catálogo y luego reportados a JetBrains.

IDEA-393501 ↗

SearchForTestsTask: non-cancellable ReadAction.run() in a background task

Abierto

Encontrado por Background ReadAction Freeze Companion. SearchForTestsTask es un Task.Backgroundable cuyo run() envuelve search() en el cancelable ReadAction.nonBlocking() y, unas líneas después, llama al onFound() hermano con el bloqueante ReadAction.run(), sin ningún checkCanceled() en toda la clase — el patrón que el Platform Blog de JetBrains señala como causa recurrente de congelamientos de la interfaz. Se presentó como IJPL-254654; JetBrains lo movió al proyecto IDEA (Java › Tests) y lo asignó a un desarrollador.

Un comentario de seguimiento (octubre de 2026) agregó dos puntos. La rama de modo smart, la predeterminada, también bloquea: llama al DumbService.runReadActionInSmartMode(), que está deprecado y usa ReadAction.computeBlocking() por dentro. Y cambiar sin más a ReadAction.nonBlocking() no es seguro, porque onFound() escribe archivos y una acción de lectura reiniciada los volvería a escribir. Las dos llamadas siguen en master a octubre de 2026.

IJPL-257836 ↗

DependenciesUsagesPanel.findUsages runs the whole dependency usage search in one non-cancellable read action

Enviado

Encontrado por el mismo control que Background ReadAction Freeze Companion, aplicado como escaneo sobre el propio master de IntelliJ. Al seleccionar un nodo en el Dependency Viewer (Code › Analyze Code › Dependencies), DependenciesUsagesPanel.findUsages() analiza todos los archivos del alcance seleccionado dentro de un único ReadAction.runBlocking() de nivel superior, en un hilo del pool. Una acción de escritura pendiente, como escribir en un editor, espera a que termine toda la búsqueda. El ticket propone la forma de arreglo que JetBrains usó en IJPL-236316 (FindUsagesHelper): una acción de lectura no bloqueante que deje de tragarse ProcessCanceledException, con la actualización de la interfaz fuera de la acción de lectura. El soporte de JetBrains pidió pasos para reproducirlo. Un test sin interfaz sobre un proyecto sintético lo reprodujo: con 2,000 archivos, una acción de escritura esperó 4.8 s a la búsqueda, y 1 ms con una acción de lectura no bloqueante. El test está adjunto al ticket, y el arreglo se propone en el pull request #3684.

Arreglos aportados

Pull requests enviados al repositorio intellij-community de JetBrains para un error reportado arriba.

PR #3684 ↗

IJPL-257836 Dependency Viewer: run the usage search in a non-blocking read action

Abierto

Arreglo para IJPL-257836. La búsqueda de usos corre en ReadAction.nonBlocking(...), que se reinicia cuando hay una acción de escritura pendiente, la misma forma de arreglo que JetBrains usó en IJPL-236316. La búsqueda no tiene efectos secundarios, así que reiniciarla es seguro, y la vista de usos se arma después de la acción de lectura. Un test nuevo retiene la búsqueda dentro de su acción de lectura y comprueba que una acción de escritura no la espera. Con los jars de IntelliJ IDEA 2025.2, la acción de escritura esperó 10,021 ms con el código actual y 3 ms con el arreglo. El test no se corrió dentro del build completo de intellij-community.

Análisis sobre tickets existentes

Comentarios de causa raíz publicados en tickets abiertos de IntelliJ Platform, cada uno a partir de la lectura del código actual en master, no de una reproducción en vivo.

IJPL-200871 ↗

CME in workspace model

Corregido

WorkspaceFileIndexDataImpl.fillPackageFilesAndDirectories() recorre un LinkedHashMap sin sincronización que puede cambiar en plena iteración, lo que produce una ConcurrentModificationException. El análisis publicado aquí ubicó esa iteración y propuso una llamada a ProgressManager.checkCanceled(). JetBrains corrigió el ticket el 2026-09-09 con un cambio distinto: las consultas por nombre de paquete ahora llaman a ensureIsUpToDate() antes de leer, de modo que el índice se actualiza primero (commit e1d600df).

IJPL-27359 ↗

CME in InspectionToolRegistrar.createTools on loading/unloading plugins

Enviado

toolFactories se recorre como una vista viva y sin sincronización de un mapa mutable dentro de createTools(), en hilos de fondo y sin read-action lock — una descarga de plugin concurrente puede modificar el mapa en plena iteración. La misma vista viva sigue en master (ahora en Kotlin), así que la falla de 2020 parece reproducible en las mismas condiciones.

IJPL-80817 ↗

Cannot create light service git4ide.repo.GitRepositoryManager because container is already disposed

Enviado

La llamada original se movió tras una reestructuración del widget, pero la búsqueda del repositorio sigue corriendo bajo el obsoleto runInReadActionWithWriteActionPriority, y ninguna de las funciones auxiliares de la nueva cadena (GitBranchUtil, DvcsUtil, GitUtil) llama a checkCanceled() — así que el cierre de un proyecto todavía puede terminar en una AlreadyDisposedException, con una ventana más estrecha que cuando se reportó.

IJPL-76141 ↗

Git Log is empty due to a StackOverflow exception in IntToIntBtree.processLeafPages

Abierto

processLeafPages se llama recursivamente sin ningún límite de profundidad de pila, así que un índice lo bastante grande desborda la pila y deja el Git Log vacío sin avisar. El mismo método falla en IJPL-250279, reportado de forma independiente cerca de un año después para la caché de compilación de JPS; los dos tickets no estaban vinculados. Corrección propuesta: reescribir el recorrido de forma iterativa.

IJPL-196254 ↗

Memory leak via ProjectRootManagerImpl::rootsChanged

Abierto

La lista changes de BatchSession solo se vacía cuando su contador pendingRootsChanged llega exactamente a 0 — pero el contador se incrementa sin el manejo de excepciones correspondiente, así que una excepción o una llamada reentrante asimétrica puede dejarlo trabado por encima de 0 para siempre, y desde ahí changes sigue creciendo con cada evento de cambio de raíces. La falta de esa red de seguridad se ve en el código; el primer desbalance exacto no se rastreó.

Sobre el catálogo

Plugins enfocados de la familia IntelliJ, cada uno hecho para una brecha real y documentada en las herramientas para desarrolladores. Cada producto del catálogo existe por una queja documentada, no por una suposición.

Por qué esta sección

La mayor parte de la evidencia del catálogo vive en el README de cada plugin. Ingeniería y evidencia reúne los pocos casos con una historia lo bastante sólida para leerse por sí sola, además de errores diagnosticados en la plataforma sobre la que corren los plugins.
